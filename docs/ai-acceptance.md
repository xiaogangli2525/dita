# 真实 HTTP 手册的 AI 验收

这套用例取自仓库中的真实 HTTP/HTTPS 手册，问题由我们构造，并非已经收集的测试人员反馈。它检查明确修改要求的执行、原文保护及扫描判断，不能代替研发审核或代表模型对所有技术问题的准确率。

## 先预检，再连接模型

在项目根目录运行：

```sh
npm run check:ai
```

此命令只读取手册，检查锚点、可编辑范围、预期替换和保护条件。显示 `ready` 表示用例准备就绪，**没有调用模型，也没有验证模型准确率**。

在正常启动的工作台中，使用 **AI 写作 → 模型设置** 配置地址、模型名和 Key。验收命令复用同一操作系统用户保存的连接，也支持已有的 `DITA_AI_*` 服务端环境变量。不要把 Key 放在命令参数、用例、Git 或验收报告中。

先运行一项，确认接口兼容：

```sh
npm run check:ai -- --live --case ssl-note
```

然后运行全部用例：

```sh
npm run check:ai -- --live
```

整套共 13 项，通常产生 13 次逻辑模型请求，按顺序执行，不自动保存或改写原手册。真实请求可能计费；接口或协议连续失败两次后停止，其余用例明确标记未运行。普通的修改质量不符合预期会继续检查后面的用例。没有可用连接时，命令退出码为 `2`，不会以模拟结果替代真实模型。

## 用例范围

| ID | 验收点 |
| --- | --- |
| `ssl-note` | SSL 提示改词，保留内联 AT 命令与周围源码 |
| `create-summary` | 修改短描述，保留其余章节内容 |
| `host-wording` | 修改服务器地址表述，保留参数、URL 和端口 |
| `instance-id` | 统一 ID 写法，保留共享范围及型号注脚 |
| `model-footnote` | 仅修改选定型号注脚，保留主文四实例说明 |
| `read-cache` | 修改缓存表述，保留 URC 和型号例外 |
| `chapter-context` | 使用章节上下文，仅修改明确指定的一处文字 |
| `continued-note` | 连续两轮修订，第二轮保留第一轮要求 |
| `missing-facts` | 未给出正确数值时，保留原文并询问研发确认值 |
| `structural-limit` | 新增章节请求说明接口限制，不谎称已完成 |
| `oxygen-guard` | 含未处理 Oxygen 修订的段落在本地拦截，不发送模型 |
| `scan-model-exceptions` | 共享说明与型号例外不误报为同条件冲突 |
| `scan-injected-conflict` | 在内存中构造同条件范围冲突，要求引用双方原文 |

明确替换类用例按完整预期源码逐字核对：漏改、多改、误改命令或注脚都判失败。这种判断适用于用例中指定的字面替换，并非对任意润色或同义改写的通用评分。两轮对话在同一原文基线上评估累计提案，与工作台应用前持续纠正方案的方式一致。

## 查看结果与复测

生成本地 JSON 报告：

```sh
node scripts/check-ai.js --live --json > ai-acceptance-report.json
```

报告包含模型名、修订规则版本、用例结果、原文/提案对照、引文和请求数，不包含连接 Key 或原始上游错误。报告中的内容可能包含文档原文，请按团队文档权限保管，不要直接提交 Git。

退出码：`0` 表示所选模式检查完成且无失败，`1` 表示失败或有停止后未运行的用例，`2` 表示缺少真实模型连接。判断是否完成模型验收必须同时检查 `mode=live`、`modelExecuted` 及各项结果；预检退出 `0` 不代表模型通过。

复测单个失败用例可以重复使用 `--case ID`。使用另一份同结构的真实文档库时，可添加 `--docs 目录`。缺失或不唯一的锚点、未进入可编辑上下文的预期文字会先失败，不能据此评价模型。路径必须位于指定文档库内，符号链接不能越出该目录。

把实际测试反馈加入 `tests/fixtures/ai-http-acceptance.json` 时，需要研发确认修改预期及型号范围。自动核对通过后，仍应在工作台人工检查正文修订、型号注脚和最终交付结果。当前自动测试使用本地兼容接口模拟器检查这套验收工具的行为；真实模型结果需要在已配置的公司接口上运行后填写。
